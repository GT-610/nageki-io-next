# nageki-io-next

[English](README.md) | 简体中文

面向 Nageki 系列的原生 x64 IO，用 C 从零编写。它读取 Nageki 兼容的 USB HID 控制器，实现 segatools 的 MU3 IO 与 Aime IO 接口，包括按键灯和读卡。

## 接口

两个 API 共 26 个导出：

- MU3 IO 0x0101：`mu3_io_init`、`mu3_io_poll`、`mu3_io_get_opbtns`、`mu3_io_get_gamebtns`、`mu3_io_get_lever`、`mu3_io_led_init`、`mu3_io_led_set_colors`
- Aime IO 0x0101：0x0100 的五个入口，加上 0x0101 新增的十二个

## 必须构建为 64 位

segatools 通过 `LoadLibraryW` 把这个 DLL 载入 `mu3.exe` 和 `amdaemon.exe`。这两个进程都是 64 位，因此 32 位版本会在加载时失败：

```
Ongeki IO: Failed to load IO DLL: 800700c1: MU3CustomIO.dll
```

`0x800700C1` 是 `ERROR_BAD_EXE_FORMAT`(193)，即位数不匹配，与导出名和 API 版本无关。`mu3hook/dllmain.c` 在 IO DLL 初始化失败时会调用 `ExitProcess`，于是进程在 Hook 运行之前就退出，表象就是 Hook 从未启动。

`scripts/build.ps1` 会读 PE 头，DLL 不是 x64 时直接让构建失败。

## 构建

需要 Visual Studio 2022 Build Tools 的 x64 编译器和 Windows SDK。

```
pwsh ./scripts/build.ps1
pwsh ./scripts/test.ps1
pwsh ./scripts/package.ps1
```

`build.ps1` 依次构建 DLL、检查 PE 头、加载 DLL 并调用其导出，最后跑一次绑定模拟。模拟照抄 segatools 的 `mu3_dll_syms` 与 `aime_dll_syms` 符号顺序及每版本的符号数量。segatools 全有或全无地绑定，遇到第一个缺失名就停，所以模拟会报告 `mu3 7/7` 和 `aime 17/17`。

`test.ps1` 跑按键映射、按键追踪、输入核心、LED 报文编码、卡号转换、摇杆转换和 HID 编解码的合成测试。`build/` 与 `dist/` 都在 gitignore 里。

## 故障处理

`mu3_io_init` 与 `mu3_io_poll` 恒返回 `S_OK`。segatools 从 `mu3_io4_hook_init`(`games/mu3hook/io4.c:35`) 调用 `mu3_io_init`，那里失败与 DLL 加载失败一样，对进程启动是致命的；poll 失败则会从 `io4_async_poll`(`common/board/io4.c:349`) 冒出来。因此控制器不在线时上报的是中性输入，而不是错误。

用 `/DMU3_IO_REPORT_DISCONNECT` 构建时，poll 会在超过 `MU3_DISCONNECT_REPORT_MS` 没有报文之后返回 `HRESULT_FROM_WIN32(ERROR_DEVICE_NOT_CONNECTED)`。这个开关用于需要可见故障码的实验。游戏是否会因此显示 IO4 报错，尚未确定。

## 输入有效性

输入是否有效由设备连接状态决定。设备连上并收到过一份有效报文之后，那份报文一直沿用，直到有更新的报文取代它、或设备消失，中间隔多久都一样。**只有更新的报文才能取代旧报文**，因为摇杆停在端点、按键被按住时，必须在整个按住期间保持有效。

部署控制器上的实测（`hid_probe.exe jitter 30000`）显示它**持续上报**，约 200 份/秒，摇杆不动时 30 秒收到 5986 份。因此实际上新报文总在几毫秒内到达，上述规则是兜底而不是常态。这也意味着在这台硬件上"设备沉默"是可检测的；真正变化触发的设备则无法把沉默与静止区分开。

有一个后果需要说明。若固件卡死但设备仍在枚举，句柄保持打开、读永不失败、报文永不到达，于是输入会**冻结在最后一帧而不是转为中性**——按住的那个键会一直按着。用沉默阈值可以检出这种情况，而 200 份/秒这个实测值正是让阈值可以安全选取的依据；目前**未实现**，因为那会重新引入上面这条规则专门要避免的按年龄失效，而它保护的正是真实按住的输入。

跨进程同理。`Local\MU3CustomIO-v1` 下的共享内存带一个 `published_ms` 心跳，由 HID worker 每轮刷新，只有这个心跳表示持有进程是否还活着，报文年龄从不参与判断。owner 消失主要靠进程句柄本身判定：读取方用 `OpenProcess` 打开 owner 的 PID，发现打不开或已收到信号即立刻判死，与心跳窗口无关。五秒窗口只是 PID 被复用或映射残留时的兜底；worker 沉默时每 50 ms 跳一次、持续上报时远快于此，所以该窗口宽达数百次 tick，这是刻意的——真正要检出的情况是 `amdaemon.exe` 消失，放宽它没有实际代价，而收窄它会在调度停顿或进程挂起时丢掉仍然有效的输入。断开与重连都会清空已存样本，旧的按键或卡号不会被重放。

共享内存读取会区分两种表象相同、但绝不能同样处理的失败。若拷贝撞上了 owner 的写入，这份拷贝是撕裂的、不可用——混合两帧会造出或吞掉按键——但 owner 仍然活着并在跳心跳，此时读取方沿用**上一份一致的样本**：那是设备真实发出过的一帧，对按住的键仍是真值；回中性会把所有按住的键放开一个 poll。若 owner 确实没了，则回中性并丢弃缓存，**已消失的持有者的按住键不会被重放**。`tests/core_tests.c` 覆盖这条策略，包括"owner 消失必须清缓存"。

## 报文布局

报文 65 字节：一个 Report ID 字节加 64 字节负载。

| 负载偏移 | 字段 |
|---|---|
| 0-9 | 按键字节，先五个左、再五个右 |
| 10-11 | 摇杆，小端 |
| 12 | 卡片扫描状态 |
| 13-22 | 卡号 |
| 23 | 操作按钮 |

按键字节非零即视为按下，所以上报 `0x00`/`0xFF` 的设备与上报 0/1 的设备表现一致。扫描状态不是 1 或 2 时按无卡处理，同一份报文的其余部分照旧使用。

## 按键解码

负载偏移 0-9 的十个离散按键字节（先五个左、再五个右）由 `src/button_map.c` 解码。每个字节只置自己那一位，不跨字节移位、不与别的字节相或。这就是**逐键独立性**：任何键的状态都无法影响另一个键的位，因此"按住哪几个键"相关的丢键不可能源自本 DLL。`tests/button_map_tests.c` **穷举全部 1024 种按键字节组合**断言这一点，而不是把它留作一句对源码的断言。

同一模块也链接进 `hid_probe.exe`，于是探针与 DLL 共用一份"哪个线上字节是哪个键、按键字段落在报文哪里"的定义。两份各推一次可能不一致，而那种不一致会误判是哪个键动了——与真实的输入故障无法区分。

已用 `hid_probe.exe dump` 的抓包确认 Report ID 字节为 `0x00`，摇杆字段位于第 11-12 字节、小端，对应负载偏移 10-11，**操作按钮位于负载偏移 23**。按键、扫描与卡号偏移仍来自对既有实现的协议分析，没有与抓包核对过，确认方式是用 `hid_probe.exe`。

同一次抓包读到了推杆后面两个后台键的取值。这一字节只出现过两个非零值：

| 取值 | 含义 |
|---|---|
| `0x03` | 进 Test 菜单的那个键：**同时声明 Test 与 Service** |
| `0x04` | 另一个键：**仅投币** |

位定义来自 segatools：`TEST=0x01`、`SERVICE=0x02`、`COIN=0x04`（[mu3io.h](legacy-repository/references/segatools/games/mu3io/mu3io.h)）。单独的 `0x02` 从未出现，因此这台控制器无法只产生一个 Service 事件；`0x03` 是固件固定填值还是另有第二个电气输入，尚未区分。`0x04` 不含 bit0，不可能开 Test 菜单，这就是无需在游戏内验证即可判定它是另一个键的依据。

有两个后果。**投币在游戏内无法验证**：`mu3hook` 是"该位为 1 就每次 poll 加一"而不是上升沿计数（[io4.c](legacy-repository/references/segatools/games/mu3hook/io4.c)），按住就会加很多币，而同一份代码树里的 `mercuryhook` 是有沿检测的。**Service 无法单独触发**：两位永远同时出现。

固件刷不了，所以分离这两个键唯一可动的地方是在 IO DLL 里改写这一字节。DLL 确实有这个能力——`mu3_io_get_opbtns` 返回什么由它自己决定——但每一位的含义由 segatools 固定，且当前实现是原样透传（`polled.operator_buttons & 7`）；任何伪造"先 Test 后 Service"序列的改法都会让这个 DLL 不再如实报告控制器的真实状态。因此**有意未实现**：两个后台键都不是必需品，能进 Test 菜单即可，不值得为此放弃"如实透传"这一性质。这不是性能考虑——该函数每次只读一个已取好的字节，加一层位运算可以忽略。

## 摇杆换算

换算在 `src/lever.c`。原版公式为：

```
lever = (short)( LeverOffset * 100 + raw * 32 * LeverSensitivity )
```

默认值 `LeverSensitivity = 1`、`LeverOffset = 0`，没有 clamp，`(short)` 收窄按模 65536 回绕。它不减零点，等于假设固件在摇杆居中时上报零。

用 `hid_probe.exe dump` 在实机的部署控制器上直接读到摇杆字段：

| 位置 | raw |
|---|---|
| 左端 | `0x032A`(810) |
| 静置 | `0x0402`(1026) |
| 右端 | `0x04A4`(1188) |

两个端点由机械限位决定，可复现。**静置值不是**：摇杆不可能精确停在电气中心，停在哪儿就读到哪儿，同一控制器后来的 `jitter` 读到的是 1035 而非 1026。`neutral` 才是硬件常量，静置读数只是某一次停放位置的观测。

电气中心是 `0x0400`(1024)，因此本构建减掉它：

```
lever = (short)( (raw - neutral) * 32 * sensitivity ),   neutral = 1024
```

### 为什么要减掉中心

中位输出变成 `(C - C) * 32 * sens = 0`，对任意灵敏度都成立。原式输出的是 `C * 32 * sens (mod 65536)`，只有 `C * sens` 为 2048 的整数倍时才归零：

| 灵敏度 | 原式中位输出 |
|---|---|
| 1, 3, 5, ... | `0x8000`（半量程） |
| 2, 4, 6, ... | `0x0000` |

2048 即 2^11，因此偶数灵敏度在 `v2(C) >= 10` 时居中，奇数灵敏度需要 `v2(C) >= 11`。两个条件同时成立，强制 `v2(C) = 10`，即 `C = 1024 * 奇数`。探针数据选定 1024：10 位范围内另一个候选 3072 距离实测静置值 2046 格。

在部署基线灵敏度 2 下，减零点的换算对**每一个** raw 都与原版逐位相同——两者相差 `1024 * 32 * sens`，当且仅当灵敏度为偶数时是 65536 的整数倍，`tests/lever_tests.c` 对全部 65536 个输入做了断言。这个改动换来的是奇数档从不可用变为可用。

### 范围与灵敏度上限

行程约 378 格，810 到 1188，因此离中心最大偏离 214 格。要让 `偏离 * 32 * sens` 留在有符号 16 位正半轴内，灵敏度上限为 4：`214 * 32 * 5 = 34240` 会回绕成负数。`MU3_LEVER_SENSITIVITY_MAX` 取 4。

只有减去中心后的低 10 位会影响结果，因为灵敏度 2 时 `1024 * 64 = 65536`。这来自原式本身，不是本实现的缺陷。

### 调参

DLL 同目录下的 `MU3CustomIO.ini` 可覆盖默认值：

```
lever_neutral=1024
lever_sensitivity=2
```

`lever_neutral` 取 0..65535，`lever_sensitivity` 取 1..4。文件不存在、或部分内容非法时保留默认值；单个键缺失时保留已有值。设 `lever_neutral=0` 可还原原版未减零点的输出。包内的 `MU3CustomIO.ini.txt` 是带注释的模板，需改名后生效。文件放在 DLL 同目录而非 exe 同目录，因为 `mu3.exe` 与 `amdaemon.exe` 加载的是同一份 DLL。

### 标定画面的读数

机台摇杆标定画面在灵敏度 2 下读左端 `B0FFH`、右端 `557FH`。两者都是奇数，且对 64 取模都为 63。而 lever 值恒为 `32 * sensitivity` 的整数倍、因此恒为偶数，不可能是这两个读数。灵敏度 2 的比例是 64，所以 `adcs[0] = 0x7FFF - lever`（`common/board/io4.c:125`）对 64 取模恒为 63，与读数完全吻合。因此画面显示的是标定信号，而不是 `mu3_io_get_lever` 的返回值。反推得到 raw 约 828 与 1194，跨度 366；探针直接测得的跨度是 378，相差 3%。

该同余关系在比例为 64 的整数倍时成立，即灵敏度 2 与 4；灵敏度 1、3 下 `adcs` 还可能 ≡ 31，而这两个读数取自灵敏度 2。

居中时读到 `0000H` 则是 lever 输出本身——在偶数灵敏度下，原式与减零点式在中心都是 0。这两个读数是不同的量，此前看上去互相矛盾正源于此。

## HID 匹配

DLL 按 VID `2341` 与 PID `8036` 匹配，不限制报文长度，输入输出都为 65 的接口优先但不作要求。读超时既不刷新也不作废已持有的输入。

报文在本 DLL 固定的 65 字节帧与描述符上报的长度之间做编解码。上报 64 字节的设备只带负载，因此写时丢掉帧的 Report ID 字节、读时补 0；若把 65 字节整帧发给这种设备，ID 字节会落到负载首字节的位置，整体前移一位并丢掉最后一个负载字节——表现为灯错位而不是明显报错。上报超过 65 字节的设备补零。这些映射由 `tests/hid_pack_tests.c` 覆盖。

一次读最多等 50 ms 就回到循环顶部；写仍按 1000 ms 等待。部署控制器约 200 份/秒持续上报，因此读实际约 5 ms 就返回，这个超时只在设备沉默时才会走完，而那时它唯一的作用是限定排队灯光帧的等待上限并保持心跳新鲜。它从不参与输入的时效判定。

输入有效性只由**读**决定。写失败或超时只丢掉那一帧排队的颜色，别的什么也不影响；设备是否真的没了，由随后的读来发现。输入与输出是两条独立路径，一次颜色写入失败不该能把按键一起带走。

控制器目前约每 200 份/秒上报，而游戏轮询远慢于此，所以报文持续堆积，除最后一份外每一份在被读到时都已被更新的取代。因此读到一份后会继续以零等待连读，**只保留最新的一份**再交给游戏；按顺序逐份喂过去，等于让游戏依次走过一串已经过期的摇杆与按键状态。上限 8 份。游戏是通过 `mu3_io_get_gamebtns` / `mu3_io_get_lever` 读取当前量的，所以被丢弃的报文不含任何游戏本可观察到的信息。

## 读卡

`scan == 1` 直接返回十个卡片字节。`scan == 2` 把前八个字节视为大端十六进制数，将其二十位十进制数字编码为十个 BCD 字节后返回。MIFARE、FeliCa 交易、读卡器灯和 VFD 入口是返回 `S_FALSE` 的占位实现，不宣称硬件并不具备的能力。

## 按键追踪

还有一套按需开启的工具，专门用于探针覆盖不了的情况：机台正被玩家占用，任何东西都无法独占设备。DLL 本来就持有设备，因此它可以在**不打扰游玩**的前提下记录控制器实际报了什么。

除非 DLL 旁边的 `MU3CustomIO.ini` 里写着，否则它是关闭的：

```
[trace]
enabled=1
```

关闭时不会打开任何文件，每份报文只多一次分支判断。开启后，两个进程各在 DLL 旁写一个日志，格式就是 `trace_analyze.exe` 读的那种：

| 文件 | 由谁写 | 内容 |
|---|---|---|
| `MU3CustomIO-wire.log` | `amdaemon.exe`（HID 持有者） | 设备直接发出的按键字节 |
| `MU3CustomIO-served.log` | `mu3.exe` | `mu3_io_poll` 交给游戏的那份样本 |

两者都用 `QueryPerformanceCounter` 打时间戳——同一台机器上跨进程可比，且细到能测出开关抖动；`GetTickCount64` 做不到，它约 15.6 ms。只写按键**变化**，所以空闲时没有任何输出。每个文件开头有一行基线，好让第一次真实变化有东西可比。

两个文件要区分的正是这件事：**线上就异常的键是控制器故障；线上干净却在 served 日志里缺失的键是软件故障**。判定硬件问题要看 wire 那份，因为按住期间触点断开在那里表现为「按下、松开、再按下」——这是设备之上任何一层都编不出来的形状。

```
trace_analyze.exe MU3CustomIO-wire.log
```

分析器逐键报告按下、松开次数，以及 **click**：同一个键在 15 ms 内松开又按下。音游里玩家不可能故意这么做，所以一次 click 就是触点弹跳——按住期间开关短暂断开。它还会报每个键见过的最短一次完整按下-松开，这是坏开关最清楚的单一特征：几百微秒不可能是手指，那是触点在通断。

两个归一化都很重要，都会打印：

- **看"每次按下的 click 率"，不是 click 绝对值。** 打得多的键在同样的故障率下 click 数天然更多，绝对数其实主要衡量你用了多少次这个键。要比较两个开关，看比率。
- **看对照。** 某个键有百分之一量级的 click 率、其余键在相近按下次数下接近零，这是同一个玩家手下两个开关之间的差别。若每个键的比率都差不多，那共同因素就是玩家或环境，不是硬件。

分析器从字节列**自行推导**每次跳变并据此判定，忽略 `down=`/`up=` 文本列，并会报告两者不一致的次数。这样即使日志的文本列写错了，结论仍然正确，而不是给出一个自信的错误答案。

## 探针

`build/hid_probe.exe` 是独立工具，游戏不会加载它。

```
hid_probe.exe              列出 HID 设备及其 VID、PID 与 caps
hid_probe.exe dump 30000   打开控制器，只打印发生变化的报文，持续 30 秒
hid_probe.exe jitter 30000 摇杆全程不动，采集 30 秒报文并统计噪声
hid_probe.exe chord 60000  十个按键字节的逐键普查，按"按下时另有三/四个键
                           已按住"分别计数
```

在插着控制器的那台机器上运行。一次只按下一个键再松开，发生变化的字节属于该键。把摇杆推到两端读取真实范围。部署控制器上的抓包已经确定了 Report ID、摇杆字段与其中位；本 DLL 里的按键、扫描与卡号偏移仍来自推断，探针是把它们变成实测值的手段。

`jitter` 测量手不碰摇杆时读数有多稳，这正是决定要不要加噪声门的依据。它打印到达速率、最小值/最大值/跨度，以及围绕 1024 的取值直方图。部署控制器上的结果是 30 秒 5986 份（约 200 份/秒）、全部为同一个值、跨度为 0，**因此不需要噪声门**：它只会压掉真实的缓慢移动。取值窗口为 ±32 格，超出窗口的样本单独计数，因为那是摇杆被推动了而不是噪声。

`jitter` 还会打印静置值及其相对 1024 的偏移。这个偏移**不是**漂移测量、**也不是**标定：摇杆是机械件，不可能精确停在电气中心，它停在哪儿就是哪儿。部署控制器静置读到 1035（+11，灵敏度 2 下约 704 单位），同一控制器此前的抓包读到 1026（+2）。这是**两次不同的摇杆停放位置，不是硬件发生了变化**，两者都不构成调整 `lever_neutral` 的理由。跨度和直方图真正确立的是：摇杆不受触碰时读数稳定且完全可复现。

`chord` 回答的是另一个问题：按住若干键、再按一个键时，控制器到底报没报这个新键？它直接读线上那十个按键字节，因此在**关闭游戏**运行的前提下，结论既不依赖本 DLL 也不依赖 segatools。它实时打印每一次变化，最后给出逐键普查，其中包括每个键"按下时另外已有 N 个键按住"的次数。某个键在"另有 4 键按住"一栏被计数到，说明控制器在那种组合下报出了它，那一按没有丢在线上，丢失发生在下游。反之，若用户确信按了、慢速重复同一组合仍从不计数，则指向控制器自身的按键扫描——矩阵 ghosting/防串键的特征，任何 DLL 改动都修不了。失败如果在组合之间游走、或者放慢就消失，更像操作时序而非设备。普查还会记录每个键出现过的不同字节值：二进制开关只该出现 `00` 与一个非零值，出现第三个值就证伪了极性模型。按键按负载偏移（`L1`..`L5`、`R1`..`R5`）报数而不是按物理键名，因为字节到键的对应仍未核对；普查只拿同一偏移与自身前后比较，所以名字对不对不影响结论。

## 部署

1. 备份在用的 IO DLL、segatools 配置和游戏存档，记录它们的路径与哈希。
2. 把新 DLL 放在单独目录，只让 segatools 的 IO 与 Aime 配置指向它。对照被替换的 DLL 逐项检查按键及其极性、摇杆中位与两端、读卡和灯光。
3. 确认断开控制器后输入转中性且不沿用上一次的按键或卡号，重新连接后输入恢复。segatools 或游戏是否会为此 DLL 报出 IO4 故障、报什么码，尚未确定。
4. 一旦出现加载失败、按键方向相反、卡片错误、灯光错位或游戏异常，退出游戏，恢复原配置与原 DLL，重启两个进程。不要在游戏运行时替换 DLL。

`amdaemon.exe` 被假定为唯一持有 HID 设备的进程。若两个进程都配置了这个 DLL 而其中只有一个能打开设备，请先确认是哪一个，再依赖共享内存通路。
